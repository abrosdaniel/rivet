# Проверка нагрузки и браузерного API

Стенд `rivet/tooling/api_load_browser.py` использует настоящий PostgreSQL и
сетевые слушатели Rivet, но только синтетические данные. Нужны Docker, Python 3
и JDK 21, выбранный через `JAVA_HOME`. Запуск из корня репозитория:

```sh
python3 rivet/tooling/api_load_browser.py /tmp/rivet-api-load-browser
```

Скрипт создаёт отдельный контейнер PostgreSQL 18 с временным паролем и удаляет его
после завершения. Порты loopback 55449, 24480–24482 должны быть свободны.
Каталог результата содержит изолированные Gradle outputs, `run.log` и `results/`.
Не используйте каталог установленного клиента или сервера.

Сначала выполняется смешанный тест 100 пользовательских идентичностей: 24 000
операций с задачами, чатом, доской и уведомлениями. Затем API-стенд проверяет:

- 2 000 HTTP-запросов при 100 параллельных клиентах и изоляцию личных задач;
- 1 000 Java API-запросов всплесками, включая ожидаемый `BUSY` при заполнении очереди;
- 100 авторизованных подписок через 13 backend WebSocket-соединений;
- 60 секунд по 100 HTTP-запросов в секунду одновременно с подписками;
- прекращение всех подписок после отзыва сессий и последующий доступ с новыми сессиями.

После `RIVET_BROWSER_READY` откройте `http://127.0.0.1:24480` в настоящем браузере
и нажмите «Запустить проверку». Страница проверяет tickets, приватную подписку,
повторное использование и истечение ticket, чужой Origin, запрет браузерной записи,
CORS и закрытие соединений после отзыва сессии/ключа. Постоянный ключ и сессия
не попадают на страницу. Ожидаемые отказы подключения видны в консоли браузера.

`results/load.json` содержит задержки и счётчики, `results/browser.json` — результат
браузера и User-Agent. Итоговый маркер браузерного запуска —
`RIVET_API_LOAD_BROWSER_OK`. `--load-only` выполняет нагрузку без ожидания браузера;
`--skip-mixed` пропускает отдельно проверяемый смешанный тест.

## Контракт и нативный сервер

| Команда | Что проверяет |
| --- | --- |
| `./gradlew :api:test` | Контракт без Minecraft и запущенного мода |
| `./gradlew :core:test --tests '*JavaWatchesTest'` | Снимки, лимиты, отмена и остановка подписок |
| `./gradlew :core:test --tests '*StatusFeedTest'` | История статуса, границы и параллельное чтение |
| `./gradlew :core:postgresTest --tests '*DomainRestTest'` | Доменные политики и подписки с тестовой PostgreSQL |
| `./gradlew :bootstrap:verifyBundle` | Совпадение классов публичного артефакта с поставляемым JAR |

Для отдельного NeoForge-сервера используйте
`python3 rivet/tooling/api_smoke.py <temporary-directory> --database-port <port>`.
Пароль задаётся через `RIVET_TEST_DB_PASSWORD`, база — `rivet_test`.
Сценарий проверяет подключение Java API, чтение из рабочего потока и отказ после
остановки. Используйте только тестовую БД: стенды очищают её данные.

## Границы проверки

Это тест API для 100 разных пользователей, не 100 запущенных Minecraft-клиентов.
Он не измеряет TPS, генерацию мира, работу клиентских модов или интернет-задержку.
Сто backend-подписок используют 13 соединений с отдельными сессиями; это не
проверка 100 одновременных браузерных WebSocket-соединений. Производственный предел
WebSocket-соединений остаётся настраиваемым в диапазоне 1–32.

Для стрессового HTTP-этапа стенд явно использует 8 workers, 128 соединений/очередь,
15-секундный deadline и бюджеты 100 000 запросов в минуту. Эти значения позволяют
измерять обработку, не упираясь в защитные квоты по умолчанию. Они не являются
рекомендацией автоматически увеличивать лимиты рабочего сервера.

Java API сохраняет два workers и очередь 64. `BUSY` при всплеске — предусмотренный
контракт; приложение должно ограничивать параллелизм и повторять запрос с задержкой.
Для изменений сохраняйте прежний ID операции. Таймаут не гарантирует отмену записи.

Браузерная страница работает через HTTP только на loopback, а тестовый объект
BrowserTickets получает этот локальный Origin непосредственно. Производственная
валидация HTTPS origins не меняется. TLS/WSS и reverse proxy проверяются отдельным стендом Nginx, описанным ниже.
CSP сайта и конфигурацию внешнего хостинга проверяет владелец приложения.
Метрики CPU/heap относятся ко всему тестовому JVM, включая генератор запросов;
они не описывают память или CPU только игрового сервера. Результаты времени зависят
от машины; тест не вводит нестабильные временные пороги CI.

## Проверка HTTPS и WSS

```sh
python3 rivet/tooling/api_proxy_smoke.py /tmp/rivet-api-proxy
```

Нужны Docker, OpenSSL, Python 3 и JDK 21. Стенд создаёт отдельный PostgreSQL 18,
Nginx с закреплённым digest образа и однодневный тестовый CA. Используются порты
55450, 24481–24484. CA доверяет только тестовый Java-клиент, системное хранилище
не меняется. Контейнеры и приватные ключи удаляются при завершении.

Проверяются отказ для недоверенного CA и неверного имени сертификата, HTTPS,
перенаправление, приватные данные и `no-store`, Origin, WSS Upgrade, подпротокол,
одноразовость и истечение ticket, запрет браузерного Bearer и прекращение доступа
после отзыва сессии или ключа. Проверяются TLS 1.2 и TLS 1.3. Результат —
`results/proxy.json` и маркер `RIVET_API_PROXY_OK` в `run.log`.
Полный CI включает этот сценарий как обязательный gate перед публикацией.
Это транспортный тест настоящего Nginx и серверных обработчиков Rivet с Java-клиентом;
[проверка в настоящем браузере](#проверка-нагрузки-и-браузерного-api) выполняется отдельно.
