# Измерение производительности

`PerformanceMetrics` сохраняет до 64 имён операций: количество, суммарное и
максимальное время, число ошибок. Записи не содержат идентификаторов игроков,
координат или содержимого запросов. Снимки неизменяемы.

Подробный режим `PerformanceMetrics.detailed(true)` дополнительно хранит последние
2048 измерений каждой операции. `distributions()` возвращает p50/p95/p99 по этому
окну методом nearest rank. Среднее и максимум из `snapshot()` относятся ко всем
записям после `clear()`, а не только к окну. `detailed(false)` освобождает окна.
Замеры частых клиентских путей выключены по умолчанию: `start()` возвращает 0,
не обращаясь к часам; `end()` ничего не записывает.

Измерены отдельными операциями сканирование карты, отрисовка миникарты,
подготовка/отрисовка меток и отрисовка большой карты. Время вложенных операций
нельзя складывать: оно уже входит во время вызывающей операции. Это время CPU
и подачи команд рендеру, не прямое измерение GPU. Большая карта отдельно измеряет поверхность,
подготовку занятых областей, метки и проверки пересечений. Для проверок
пересечений число вызовов отличается от числа кадров: среднее время на кадр
считается как суммарное время проверок, делённое на число отрисовок карты. `database.acquire` отражает
успешное получение соединения в подробном режиме; существующая
`database.transaction` включает полную транзакцию и её ошибки.
`map.positions.policies` и `map.positions.groups` измеряют запросы политик
видимости и членства; второй выполняется только для видимых кандидатов с
аудиторией объединений. Эти операции не включают остальные SQL обработчика.

## Нативный клиентский сценарий

`PerformanceBaselineHarness` доступен с `-PrivetUiHarness`. Задайте:

- `RIVET_PERF_ADDRESS`: адрес подготовленного тестового сервера;
- `RIVET_PERF_OUTPUT`: путь к итоговому JSON;
- `RIVET_PERF_WORLD_ONLY=true`: только большая карта с 4096 метками, три повтора.

Запустите `:mod:runClient -PrivetUiHarness` с окном 1280×1024. Сценарий использует
GUI 2, 100 тиков первоначального прогрева, затем по 40 тиков прогрева и 120 тиков
сбора на сцену. Шесть сцен повторяются трижды: миникарта с 0/100/1000/4096 метками,
вращение с 4096 метками и большая карта с 4096 метками. Итоговый маркер успеха —
`RIVET_PERFORMANCE_OK scenes=18` (либо `scenes=3` для большой карты). Синтетические метки не сохраняются в личное
хранилище: сценарий временно подменяет репозиторий и восстанавливает состояние.
Используйте отдельный игровой профиль и сервер для тестов.

JSON содержит настройки окна/дальности/FPS, Java, ОС, число процессоров,
размер heap, распределения времени, heap до/после и время сборки мусора.
Heap до/после не измеряет скорость выделения объектов и не доказывает утечку.
Интервалы между кадрами включают ограничитель FPS и ожидания. 120 игровых тиков
номинально занимают 6 секунд; при задержках реальная длительность может отличаться.
Сценарий не измеряет холодную загрузку 50k чанков, серверную нагрузку большого
онлайна, GPU-память или многочасовой рост памяти. Для этого нужны отдельные прогоны.

Сравнивайте одинаковые версии окружения, настройки, данные и инструментирование.
Проверяйте три повтора и отдельно время выбранной операции; ускорение её CPU-пути
не означает такое же увеличение FPS. Не запускайте принудительную перекомпиляцию
в том же каталоге сборки параллельно работающему dev-клиенту/серверу.


## Снимки позиций игроков

Опциональная возможность `map-position-pages` согласуется при подключении.
При её наличии один `mapPositionPeers` запрашивает до 4096 доступных кандидатов.
Политики приватности читаются в фоне, координаты и расстояния проверяются
на серверном потоке непосредственно перед ответом. Проверка ревизии отсекает
изменение прав во время чтения БД. Политики не передаются клиенту.

Ответ разбивается на компактные JSON-пакеты: до 384 записей, словарь измерений,
`positionPage` с нуля и `positionLast`. Страницы отправляет сервер без отдельных
клиентских запросов. Сериализация этого ответа без отступов; каждая строка
проверяется на предел 32767 символов сетевого кодека. Внутренний бюджет данных
страницы — 30000 символов с резервом для служебных полей.

Клиент сопоставляет все страницы с идентификатором запроса, проверяет порядок,
ревизию, UUID, координаты и общий предел; публикация атомарная после последней
страницы. Срок жизни — 7 секунд от начала запроса, получение очередной страницы
его не продлевает. Отзыв видимости отменяет накопление; поздние пакеты отменённого
запроса не восстанавливают данные. При потере/задержке ответа за пределы срока
снимок отбрасывается. Координаты не записываются на диск.

Запросы нового режима ограничены сервером одним в секунду на клиента;
клиент начинает следующее обновление через секунду после завершения ответа.
Без согласованной возможности используется прежняя пагинация по 64 кандидата.
Сервер свыше 4096 кандидатов возвращает ошибку вместо обрезанного снимка.
Большой онлайн всех получателей требует отдельного нагрузочного теста: размер
одного снимка не характеризует суммарную пропускную способность сервера.


## Нагрузка чтения позиций

`PositionFanoutLoadTest` запускается отдельно на изолированной тестовой PostgreSQL:
`RIVET_POSITION_LOAD=true RIVET_POSITION_LOAD_OUTPUT=/tmp/position-load.json ./gradlew :core:postgresTest --tests dev.abros.rivet.core.PositionFanoutLoadTest --rerun`.
Нужны те же переменные подключения, что для остальных PostgreSQL-тестов.
Тестовая база очищается; рабочую базу использовать нельзя.

Сценарий выполняет реальные запросы политик и сериализацию для 10/50/100
синтетических получателей, по три повтора. Сравниваются одновременная подача
и расписание по UUID в пределах секунды с округлением до тиков 50 мс,
с моделируемым ожиданием следующей границы
50 мс и без него. Очередь: два исполнителя, 64 ожидающих запроса.
Результат содержит p95 ожидания/ответа/упаковки, отказы, пик очереди и байты JSON.
Маркер завершения: `RIVET_POSITION_LOAD_OK scenarios=36`.

Это модель очереди, а не Minecraft с таким количеством подключений: она
не измеряет фактический игровой тик, сетевой кодек/сжатие, конкурентные запросы
меню и скинов или окончательную фильтрацию координат на игровом потоке.
Время не является порогом CI. Обычные прогоны тест пропускают.

Первый опрос позиций распределён по UUID клиента в пределах 0–999 мс.
Ошибка или истечение запроса очищает снимок и включает повтор через
1–1.999, затем 2–2.999, далее 4–4.999 секунды. После успешного снимка
интервал снова равен одной секунде; новая сессия сбрасывает накопленную
задержку. Отзыв доступа очищает координаты немедленно. Срок свежести
снимка считается от отправки запроса, а не от начала ожидания опроса.
Ограниченная серверная очередь сохраняет защиту от клиентов без распределения
запросов и от конкурирующей нагрузки других модулей.


## Настоящий сервер: очередь и смешанные чтения

В сборке с `-PrivetUiHarness` переменная `RIVET_SERVER_LOAD_OUTPUT`
включает `ServerLoadHarness` и задаёт путь отчёта JSON. Используйте отдельный
dev-сервер с включёнными главной, объединениями, событиями и объявлениями,
затем подключите клиент `RivetMapTest` с согласованным `map-position-pages`.
Сценарий сам не создаёт документы и не меняет настройки приватности.

Трижды выполняются фазы по 200 тиков: простой, только позиции и смесь
позиций с четырьмя разделами меню. В активных фазах подаются пять чтений
за тик (100/с при 20 TPS) через настоящую общую очередь ServerFeatures
и PostgreSQL. Чтения меню сохраняют предварительную передачу управления
игровому потоку. Позиции проходят реальные prepare/fill и сериализацию;
тестовые ответы отбрасываются, не рассылаются клиентам. После каждой
фазы очередь дожидается завершения. Маркер: `RIVET_SERVER_LOAD_OK phases=9`.

Отчёт содержит число завершений/отказов, максимальную наблюдавшуюся очередь,
распределения ожидания, чтения, подготовки ответа и тела игрового тика.
`load.*.read` включает ожидание предварительной проверки для меню.
`server.tick.body` измеряется между событиями Pre/Post и не включает
всю работу Minecraft между тиками; callbacks измеряются отдельно.

Это синтетические запросы одного подключённого пользователя с текущими
данными dev-сервера. Ограничитель частоты сетевых запросов в тесте обходится,
поэтому сценарий изучает исполнители и БД, а не полный сетевой путь.
Он не воспроизводит 100 соединений, большой список онлайн-игроков, плотную
БД, запись задач, загрузку скинов или сетевое сжатие. Первая фаза может
включать прогрев мира. После завершения детальные таймеры выключаются.

В обычном серверном коде таймеры `map.positions.prepare` и
`map.positions.fill` используют общий механизм PerformanceMetrics и
не читают часы, пока детальная диагностика выключена.


## Списки на большой тестовой базе

Opt-in `CommunityLargeReadTest` создаёт в изолированной PostgreSQL 6000
документов и 96000 связей. Запуск: `RIVET_LARGE_READ=true
RIVET_LARGE_READ_OUTPUT=/tmp/large-read.json ./gradlew :core:postgresTest
--tests dev.abros.rivet.core.CommunityLargeReadTest --rerun` с переменными
подключения тестовой базы. Рабочую базу использовать нельзя: TestDatabase
очищает таблицы. Маркер: `RIVET_LARGE_READ_OK documents=6000 relations=96000 scenarios=8`.

Измеряются списки объединений, событий, объявлений и главной, с поиском
редкого названия и без него. Один предварительный запрос и пять измерений
на сценарий; JSON содержит медиану, максимум и контрольную сумму результатов.
Тест подтверждает повторяемость страницы, не задавая хрупких порогов времени.
Он измеряет SQL-списки, а не интерфейс, сеть или запись задач.

Списки отбирают документы и проверяют наличие связей до восстановления
коллекций участников/откликов/голосов. Материализованная выборка ограничена
11 документами; полное представление строится только для этой страницы.
Повторная сортировка сохраняет порядок и продолжение страницы при одинаковом
времени событий. Существующие индексы связей используются без миграции данных.


## Большие списки задач

`TaskLargeReadTest` включается через `RIVET_TASK_LOAD=true` и записывает
JSON по `RIVET_TASK_LOAD_OUTPUT`. Запускайте `:core:postgresTest --tests
dev.abros.rivet.core.TaskLargeReadTest --rerun` только на изолированной
тестовой базе: TestDatabase очищает таблицы. Набор: 6000 задач, объединение
с 1000 участниками, по 40 комментариев и 20 записей истории на задачу.
Шесть сценариев проверяют личный/групповой список со статусом open, поиск
по названию и коду. После предварительного запроса выполняются семь замеров.
Маркер завершения: `RIVET_TASK_LOAD_OK tasks=6000 members=1000 scenarios=6`.
Маркер `RIVET_TASK_PAYLOAD` сообщает размер полного и сокращённого JSON
одной тестовой задачи, до протокольного оформления и сетевого сжатия.

SQL материализует не более 21 задачи для страницы, затем исключает
комментарии, историю, склады, зависимости и резервы из данных списка.
Полные карточки продолжают читать сохранённые поля. Материализация
ограничивает стоимость преобразования JSON выбранной страницей;
фильтры, курсор, авторизация и правила выдачи кодов остаются прежними.


Поиск задач использует вычисляемые PostgreSQL-поля `task_search`,
`task_status` и `task_archived`. Они автоматически обновляются из `body`
при любой записи, включая прямые SQL-обновления; отдельного фонового
индексатора и риска отставания копии нет. Строка поиска сохраняет исходную
семантику: название, пробел, описание, пробел, код; регистр обрабатывается
PostgreSQL, `%` и `_` остаются буквальными символами.

Миграция 007 автоматически заполняет поля существующих записей при запуске
сервера. Исходные JSON, ревизии и коды не меняются. Поля занимают дополнительное
место для названия/описания/статуса; миграция обрабатывает существующую таблицу,
поэтому её время зависит от размера базы.

`TaskLargeReadTest` также сохраняет `<RIVET_TASK_LOAD_OUTPUT>.plans.json`
с `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)` того же SQL и параметров. План
снимается отдельным подготовленным выражением: он может отличаться от
плана повторно используемого JDBC-запроса. Для пользовательской задержки
сравнивайте замеры полного `store.request`, а не только Execution Time.


## Полные карточки задач

Зависимости карточки читаются одним запросом вместе с кодами и краткими
полями. Выдача сохраняет порядок исходного списка, блокирующие записи
удалённых задач и ограничение владельцем/объединением. Пустой список
не обращается к БД. Диагностический таймер `task.dependencies.query`
использует общий opt-in механизм PerformanceMetrics. Если у задачи нет
ресурсных требований, общий складской запас не просматривается; сведения
о привязках самой задачи и резервах продолжают формироваться.

Opt-in `TaskDetailLoadTest`: `RIVET_TASK_DETAIL_LOAD=true`, путь отчёта
`RIVET_TASK_DETAIL_LOAD_OUTPUT`, задача `:core:postgresTest --tests
dev.abros.rivet.core.TaskDetailLoadTest --rerun`. Используйте только
изолированную тестовую базу с переменными подключения TestDatabase.
Набор: 11 задач с комментариями/историей и 704 складские привязки.
Шесть сценариев комбинируют 0/1/10 зависимостей и наличие ресурсов.
После предварительного запроса выполняются девять измерений полной
карточки с проверкой неизменности ответа. Маркер:
`RIVET_TASK_DETAIL_LOAD_OK tasks=11 stocks=704 scenarios=6`.


## Изменение цепочек и проверка прав задач

При изменении зависимостей каждый узел графа читается один раз за операцию.
Локальная таблица узлов не переживает запрос. Каждая корневая зависимость
сохраняет отдельный обход и прежний предел 200 узлов, включая проверку цикла
до повторного использования узла. Читаются только связи, владелец и группа.
Таймер `task.graph.query` доступен через опциональную подробную диагностику.

Права задач объединения проверяются по текущим статусу группы, владельцу
и роли конкретного игрока. Полный состав группы для этого не загружается;
права между запросами не кешируются. Закрытая группа, отключённые модули
и ограничения личных задач сохраняют прежние правила.

Opt-in `TaskGraphLoadTest`: `RIVET_TASK_GRAPH_LOAD=true`, путь результата
`RIVET_TASK_GRAPH_LOAD_OUTPUT`, запуск `:core:postgresTest --tests
dev.abros.rivet.core.TaskGraphLoadTest --rerun` на изолированной базе.
Сценарии: десять зависимостей с общей цепочкой из ста задач и проверка
прав в группе с 1000 участниками. Девять замеров после предварительного
запроса. Маркер: `RIVET_TASK_GRAPH_LOAD_OK nodes=110 members=1000 scenarios=2`.
