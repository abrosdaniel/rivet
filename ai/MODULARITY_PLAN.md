# План модульной архитектуры

Статус: реализованы внутренние точки сборки, серверный жизненный цикл,
разделение обработчиков оформления/чата/навигации и владение серверными потоками.
Проверено: сборка и упаковка одного JAR, 318 Java-тестов (включая 8 тестов
жизненного цикла), клиентские native-сценарии (54 кадра без PNG), запуск/остановка
реального сервера с включёнными и выключенными функциями, базовая авторизация,
чат/метаданные/навигация и очистка соединения с LuckPerms, Plasmo Voice и Xaero’s.
58 тестов инструментов также прошли. GitHub CI в этой задаче не запускался.

Цель: независимые внутренние модули, один устанавливаемый JAR;
сохранить существующие настройки, данные и пользовательские сценарии.

1. Составить карту зависимостей функций, общих служб и адаптеров; измерить
   вклад кода, ресурсов и библиотек в размер поставки.
2. Определить границы: основа, оформление игроков, чат, навигация, скины,
   социальные функции, авторизация. UI Kit и доступ к БД — общие службы.
   Сохранить core независимым от Minecraft.
3. Ввести жизненный цикл: условия доступности на клиенте/сервере, запуск,
   остановка, освобождение ресурсов, регистрация команд и сообщений.
   Отключённые функции не выполняют фоновые задачи, сбор данных и обмен пакетами.
4. Обращаться к LuckPerms, Plasmo Voice, Xaero’s, spark и остальным интеграциям
   только через адаптеры. Проверить отсутствие и несовместимость API.
5. Переносить последовательно: оформление игроков → чат → навигация → скины
   → социальные функции → авторизация. После каждого переноса проверять поведение.
6. Сохранить имена и значения конфигурации. Общий выключатель каждого внутреннего
   модуля добавлять только при практической необходимости. Новые настройки должны
   появляться в файле с пояснениями и резервным копированием.
7. Собирать один JAR без тестовых классов. Документировать архитектуру для
   разработчиков отдельно от инструкций игроков и владельцев серверов.

Не выпускать публичный Core API без конкретного самостоятельного расширения
или внешнего потребителя. Переработка отдельно разрешена пользователем после очистки документации.


## Состав поставки

Замер собранного JAR: примерно 13,6 МиБ. Сжатые вложенные библиотеки — около
11,3 МиБ, код — 1,44 МиБ, helper — 0,68 МиБ, остальные ресурсы — 0,09 МиБ.
Внутренние модули не убирают эти зависимости из единого файла. Основная выгода
текущего разделения — владение состоянием, независимая регистрация и очистка.


## Границы текущей реализации

Функции разделены точками сборки, обработчиками и владельцами ресурсов.
Сохраняются пакеты классов и существующий сетевой транспорт; перестановка всех
классов по новым Gradle-подпроектам не нужна для единого JAR. Поля статистики,
социальные разделы и голосования используют существующую конфигурацию.
Выключатели интеграций не добавляются; функциональные модули управляются своей секцией enabled.

## Следующий этап: независимые функциональные модули

Статус: пункты 2 и 3 реализованы и проверены. Выпуск отложен; версию не менять
до отдельной подготовки выпуска. Следующий модуль — карта по FUTURE_MODULES.md.

Реализованы независимые границы, условия включения и жизненный цикл:

- Объединения: участники, роли, приглашения, общие данные.
- Задачи: личные и общие задачи, этапы, комментарии, сроки.
- Хранилища и снабжение: привязанные хранилища, потребности задач,
  информация над сундуками.
- Доска объявлений: объявления, категории, отклики.
- События: расписание, участники, места проведения.
- Опросы и предложения: обычные голосования и идеи игроков; независимо
  от уже существующих голосований о наказании.
- Обращения и модерация: жалобы, ответы администрации, действия
  и история наказаний.
- Управление сервером: обслуживание, запланированная остановка,
  объявления администрации.
- TAB и имена над головой: независимые части оформления с общими
  метаданными игроков.

Документные функции маршрутизируются через CommunityModules; задачи имеют
отдельный сервис, хранилища, обращения и управление сервером — владельцев
ресурсов. Личные задачи работают без объединений. Хранилища требуют задач;
противоречивый конфиг отклоняется до запуска. TAB и имена регистрируются
отдельно в ClientModules. Общая документная модель и транспорт сохранены.

Уведомления, поиск, права, UI Kit и доступ к БД остаются общими службами
для включённых функций, без отдельных пользовательских выключателей.
Серверный конфиг должен действительно отключать ненужные функции,
а не только скрывать разделы меню. Требования к переключателям и будущей
карте записаны в FUTURE_MODULES.md. Сохранить данные и существующие диалоги,
не превращать архитектурное разделение в изменение пользовательских сценариев.

Новые идеи журнала мира, каталога ресурсов, логистики и торговли пользователем
не приняты; не включать их в утверждённый объём работ.

Проверены unit-тесты и тесты с PostgreSQL: прямые запросы к отключённым функциям,
сохранение данных при очистке, личные задачи без объединений, повторение задач
и временные объединения. Настоящий сервер запускался и останавливался с обычной
конфигурацией, отключёнными функциями и базовой авторизацией. Нативный клиент
проверил политику меню и прав, TAB — 126 сценариев GUI 1/2/3. 66 тестов инструментов
прошли. Новые поля автоматически добавляются с комментариями и резервной копией.
GitHub CI этих изменений не запускался.
